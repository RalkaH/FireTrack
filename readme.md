# 🔥 FireTrack — Система отметки проверки средств пожаротушения

[![Тесты](https://github.com/RalkaH/FireTrack/actions/workflows/tests.yml/badge.svg)](https://github.com/RalkaH/FireTrack/actions/workflows/tests.yml)
![Версия](https://img.shields.io/badge/Версия-1.4.0-blue)

**FireTrack** — это автоматизированная система учета и контроля состояния первичных средств пожаротушения (огнетушителей) на промышленных, складских и административных объектах.

Проект предназначен для замены бумажных журналов проверок, автоматизации контроля технического обслуживания и формирования цифровой отчетности для внутренних проверок и надзорных органов.

Система помогает:
- минимизировать человеческий фактор;
- централизованно хранить данные об оборудовании;
- отслеживать сроки проверок, перезарядки и срок службы;
- формировать отчеты для печати (Excel, PDF), в том числе журнал ТО по форме СП 9.13130.2009;
- видеть, кто и что менял в системе (журнал действий);
- соответствовать требованиям ГОСТ Р 51057-2001, СП 9.13130.2009 и Правил противопожарного режима.

## 🕓 История версий

### V4 (1.4.0) — ноябрь 2026: пользователи, журнал действий, сроки, отчеты

- **Админка пользователей.** Раздел «Администрирование → Пользователи»: создание, смена роли, блокировка, сброс пароля. Защита от блокировки себя и от потери последнего администратора. Роли admin, engineer и viewer теперь работают по-настоящему, а не только на бумаге.
- **Смена пароля.** Любой пользователь меняет свой пароль из меню у имени в шапке. После сброса пароля админом и для администратора с паролем по умолчанию `admin123` система требует сменить пароль при входе и до этого не пускает к данным.
- **Отзыв сессий.** Смена или сброс пароля, блокировка и смена роли сразу завершают все сеансы пользователя.
- **Защита от перебора паролей.** После 5 неудачных попыток входа подряд вход для пары «логин + IP» блокируется на 10 минут.
- **Журнал действий (аудит).** Кто, когда, с какого IP и что сделал: создание, изменение «было и стало» по каждому полю, удаление, импорт, входы (в том числе неудачные), смена пароля, выгрузка отчетов. Страница с фильтрами и выгрузка в CSV.
- **Сроки перезарядки и срок службы.** Интервалы по виду огнетушащего вещества из таблицы 1 СП 9.13130.2009, срок службы по ГОСТ Р 51057-2001, переопределение по паспорту в карточке, кнопка «Отметить перезарядку», блок на дашборде. Просроченная перезарядка ставит статус «Требует обслуживания» (отключается в настройках).
- **Отчеты для печати.** Раздел «Отчеты»: журнал проверок, журнал ТО огнетушителей по форме Г.2 СП 9.13130.2009 и «Состояние парка». Форматы: оформленный Excel и страница для печати или сохранения в PDF.
- **Настройки.** Название организации и ответственный для шапки и подписи отчетов, интервалы перезарядки, срок службы.
- **Миграции базы (Alembic).** Схема базы обновляется автоматически при запуске, данные сохраняются, перед изменением делается резервная копия.
- **CI.** Тесты запускаются в GitHub Actions на каждый push (Python 3.13 и 3.15), тестов стало 53.

> ⚠️ **После обновления до V4.** Отметок о перезарядке в базе еще нет, поэтому срок считается от даты изготовления, и у части старых огнетушителей перезарядка окажется просроченной («Требует обслуживания»). Отметьте фактические перезарядки кнопкой «Отметить перезарядку» или временно отключите правило в «Настройках». Если вы входите как `admin` с паролем `admin123`, система попросит его сменить.

### V3 (1.3.0) — октябрь 2026: исправления и безопасность

Исправлена истекшая сессия (раньше страницы просто не открывались), все API закрыты авторизацией, права ролей проверяет сервер, `SECRET_KEY` вынесен из кода, логика статусов вынесена в `status_logic.py` и исправлена, убраны дубли на дашборде, закрыт XSS, исправлена ошибка 422 при редактировании, улучшен импорт CSV, появились автотесты.

### V2 и V1 — весна 2026: курсовая работа

Исходная версия, новый фронтенд, docstrings, Docker, документация Sphinx.

## 🚀 Основные возможности

*   **Учет огнетушителей:** тип, инвентарный номер, место, статус, даты изготовления, ввода и перезарядки.
*   **Электронный журнал проверок:** фиксация каждой проверки с показаниями и состоянием узлов.

*   **Пользователи и роли:** управление учетными записями из интерфейса.
*   **Журнал действий:** полная история изменений для разбора инцидентов.
*   **Импорт и экспорт:** CSV в обе стороны.

## 🔐 Ролевая модель и пользователи

В системе 3 роли доступа (RBAC):

| Роль | Возможности |
|---|---|
| admin | Все возможности инженера, плюс удаление огнетушителей, управление статусами, пользователями, настройками и просмотр журнала действий |
| engineer | Проведение проверок, отметка перезарядки, добавление и редактирование оборудования, мест и сотрудников, импорт |
| viewer | Только чтение: дашборд, списки, журнал проверок, отчеты |

Пользователями управляет администратор в разделе **Администрирование → Пользователи**. Новому пользователю выдается временный пароль, который нужно сменить при первом входе. Удалять пользователей нельзя намеренно: заблокированная учетная запись остается в журнале действий.

Требования к паролю: не короче 8 символов, не совпадает с логином, не из списка самых простых.

Все эндпоинты API, кроме `/health` и страницы входа, требуют JWT-токен. Интерфейс скрывает кнопки, на которые у роли нет прав, но проверку прав всегда выполняет сервер.

## 📥 Установка и запуск (Локально)

### Шаг 1. Клонирование репозитория

```bash
git clone https://github.com/RalkaH/FireTrack.git
cd FireTrack
```

### Шаг 2. Создание виртуального окружения и установка зависимостей

Для Windows (PowerShell):

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

Для Linux/macOS:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

Установка зависимостей:

```bash
pip install -r requirements.txt
```

### Шаг 3. Запуск приложения

```bash
python -m uvicorn main:app --reload
```

Приложение будет доступно по адресу: http://127.0.0.1:8000

При первом запуске создается администратор `admin` с паролем из `ADMIN_PASSWORD` (по умолчанию `admin123`). Пароль по умолчанию система попросит сменить при первом входе.

### Шаг 4. Настройки (переменные окружения)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DATABASE_URL` | `sqlite:///./fire_extinguishers.db` | Строка подключения к БД |
| `SECRET_KEY` | генерируется в файл `.secret_key` | Ключ подписи JWT. Если не задан, создается автоматически при первом запуске и сохраняется, поэтому вход не сбрасывается после перезапуска |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `480` | Время жизни сессии в минутах |
| `ADMIN_PASSWORD` | `admin123` | Пароль администратора, создаваемого при первом запуске |
| `STATUS_RECALC_INTERVAL_MINUTES` | `60` | Как часто сервер сам пересчитывает статусы огнетушителей |
| `LOGIN_MAX_FAILURES` | `5` | Сколько неудачных попыток входа подряд допускается |
| `LOGIN_LOCK_MINUTES` | `10` | На сколько минут блокируется вход после них |

Когда сессия истекает, интерфейс сам возвращает на страницу входа с сообщением «Сессия истекла».

Настройки, которые меняются из интерфейса (организация, ответственный, интервалы перезарядки), находятся в разделе **Администрирование → Настройки**.

### Автоматические тесты

```bash
python -m pytest -q
```

Тесты используют отдельную временную базу и не трогают рабочую. Те же тесты запускаются в GitHub Actions на каждый push в `main` (значок «Тесты» в начале README).

## 🧬 Миграции базы данных

Схема базы описана миграциями Alembic в папке `migrations/`. Ничего запускать вручную не нужно: при старте сервер сам доводит базу до последней версии.

1. База, созданная до V4 (без таблицы `alembic_version`), автоматически помечается начальной ревизией `0001_baseline`.
2. Если есть невыполненные миграции, перед ними файл базы копируется в папку `backups/` (в git не попадает).
3. Выполняется `alembic upgrade head`, данные сохраняются.

Команды для разработки:

```bash
python migrate.py                       # обновить базу вручную
alembic current                         # текущая версия схемы
alembic revision -m "описание"          # новая миграция (после изменения models.py)
alembic check                           # проверить, что модели и миграции совпадают
```

## ⚙️ Правила расчета статусов

Статус огнетушителя определяется по его последней проверке и сроку перезарядки:

| Ситуация | Статус |
|---|---|
| Проверок еще не было | Просрочено |
| При проверке найден дефект (неисправен, пломба/чека/шланг повреждены или отсутствуют) | Требует обслуживания |
| Просрочена перезарядка (если правило включено в настройках) | Требует обслуживания |
| Дата следующей проверки прошла | Просрочено |
| Иначе | Актуально |

Статусы «Списан» и «На техническом обслуживании» ставятся вручную и автоматикой не меняются.
Новая проверка и отметка перезарядки сразу пересчитывают статус огнетушителя (кроме списанных). Весь парк
пересчитывается при запуске сервера и далее раз в час, а также по кнопке «Пересчитать статусы».

## 🔄 Сроки перезарядки и срок службы

Кроме плановых осмотров FireTrack следит еще за двумя сроками.

**Перезарядка.** Вид огнетушащего вещества определяется по типу огнетушителя, интервалы по умолчанию взяты из таблицы 1 СП 9.13130.2009 («не реже»):

| Тип | Вещество | Перезарядка |
|---|---|---|
| ОВ, ОВЭ | вода, вода с добавками | 1 раз в год |
| ОВП | пена | 1 раз в год |
| ОП | порошок | 1 раз в 5 лет |
| ОУ | углекислота | 1 раз в 5 лет |
| ОХ | хладон | 1 раз в 5 лет |

Для водных и пенных огнетушителей с полимерным покрытием корпуса, корпусом из нержавеющей стали или стабилизированным зарядом СП разрешает периодичность изготовителя: ее задают в карточке огнетушителя («Интервал перезарядки»). Отсчет идет от даты последней перезарядки, а если ее нет, от даты изготовления.

**Срок службы.** По умолчанию 10 лет от даты изготовления: для перезаряжаемого огнетушителя с металлическим корпусом это минимум по п. 5.53 ГОСТ Р 51057-2001. Точный срок указан в паспорте, его тоже можно задать в карточке.

Интервалы по умолчанию меняются в **Настройках**. Там же можно отключить правило, по которому просроченная перезарядка ставит «Требует обслуживания».

## 🖨 Отчеты для печати

Раздел **Отчеты** доступен всем ролям. Для каждого отчета выбирается период и формат.

| Отчет | Что внутри | Форматы |
|---|---|---|
| Журнал проверок | Все проверки за период, строки с дефектами подсвечены | Печать / PDF, Excel, CSV |
| Журнал ТО огнетушителей | Рекомендуемая форма Г.2 приложения Г СП 9.13130.2009: проверка узлов, ОТВ, индикатора давления, перезарядка | Печать / PDF, Excel |
| Состояние парка | Сводка по статусам и местам, проблемные огнетушители, ближайшие проверки, перезарядка, срок службы | Печать / PDF, Excel |

Excel-файлы оформлены для печати: шапка с названием организации и периодом, закрепленная строка заголовков, границы, формат дат, альбомная A4 по ширине страницы, номера страниц и строки для подписи ответственного. PDF делается через страницу печати: «Печать / PDF», затем «Сохранить как PDF» в окне печати браузера (никаких дополнительных программ не нужно).

По п. 60 Правил противопожарного режима (постановление Правительства РФ № 1479) учет наличия, осмотров и сроков перезарядки огнетушителей ведется в журнале эксплуатации систем противопожарной защиты; журнал ТО по форме Г.2 можно вести как его раздел.

## 🕵️ Журнал действий

Раздел **Администрирование → Журнал действий** (только admin). В журнал попадают:

- создание, изменение и удаление огнетушителей, проверок, мест, сотрудников, статусов, пользователей и настроек;
- для изменений — «было и стало» по каждому полю;
- импорт CSV (сколько создано, сколько ошибок и первые ошибки);
- входы, неудачные входы (с введенным логином), блокировка входа после перебора;
- смена и сброс пароля, блокировка и разблокировка пользователей;
- ручной пересчет статусов и выгрузка отчетов.

У каждой записи есть время (UTC), пользователь, IP-адрес (и `X-Forwarded-For`, если он есть) и User-Agent. Пароли и хеши в журнал не попадают никогда. Журнал фильтруется по периоду, пользователю, действию, типу объекта и тексту и выгружается в CSV.

## 🔌 Примеры API запросов

### Авторизация (Получение токена)

**POST /auth/token**

*(Примечание: Используется формат Form-Data (application/x-www-form-urlencoded), а не JSON)*

```text
username=admin&password=<пароль>
```

Ответ:

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "bearer",
  "expires_in": 28800,
  "must_change_password": false
}
```

Если `must_change_password` равен `true`, до смены пароля через `POST /auth/change-password` остальные запросы вернут 403 с заголовком `X-Password-Change-Required: 1`.

### Получение списка огнетушителей

**GET /extinguishers/**

Требуется заголовок: `Authorization: Bearer <token>`

Ответ (сокращенно):

```json
[
  {
    "id": 1,
    "inventory_number": "ОП-001",
    "type": "ОП-5",
    "status_id": 1,
    "last_recharge_date": "2025-03-01",
    "agent_label": "Порошок",
    "next_recharge_date": "2030-03-01",
    "recharge_state": "ok",
    "service_end_date": "2034-01-10",
    "service_state": "ok"
  }
]
```

### Отметка перезарядки

**POST /extinguishers/{id}/recharge**

```json
{ "recharge_date": "2026-11-05", "comment": "ООО «Пожсервис», акт № 17" }
```

## 📤 Импорт и экспорт данных

Импорт выполняется из CSV (разделитель `;`, кодировка UTF-8 или Windows-1251, как сохраняет Excel).
Строки с ошибками пропускаются, а по каждой выводится причина (дубликат, неизвестное место,
неверная дата и т.п.). Даты принимаются в форматах `ГГГГ-ММ-ДД` и `ДД.ММ.ГГГГ`.

В импорте огнетушителей есть необязательные колонки сроков: `last_recharge_date`, `recharge_interval_months`, `service_life_years`.

Экспорт: журнал проверок в CSV (формат совпадает с импортом), отчеты в Excel и PDF (см. «Отчеты для печати»), журнал действий в CSV.

## 🛡 Безопасность

- Ограничение доступа по ролям (RBAC), права проверяет сервер.
- Защита маршрутов через JWT-токены с версией: смена или сброс пароля, блокировка и смена роли сразу отзывают все сеансы пользователя.
- Обязательная смена временного пароля и пароля по умолчанию.
- Защита от перебора паролей: временная блокировка входа после серии неудачных попыток.
- Одинаковое время ответа для существующего и несуществующего логина.
- Журнал действий с IP и User-Agent, без паролей и хешей.
- Надежное хеширование паролей (PBKDF2-SHA256).
- Ключ подписи JWT не хранится в коде: берется из `SECRET_KEY` или генерируется автоматически.
- Экранирование пользовательских данных в интерфейсе (защита от XSS).
- Строгая валидация входящих данных через Pydantic.
- Резервная копия базы перед каждой миграцией схемы.
