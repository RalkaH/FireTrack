# FireTrack: контекст проекта для Claude Code

Этот файл Claude Code читает автоматически при запуске в папке проекта. Здесь собрано всё, что нужно знать о проекте: что это, где что лежит, как запускать, какие решения уже приняты и что делать дальше.

## Общение и оформление

Отвечай на русском. Не используй маркированные списки в ответах, вместо них пиши абзацами, нумерованными списками или таблицами. Не используй длинные тире. Владелец любит подключать Claude к своим сервисам (MCP, расширения, CLI), поэтому если для задачи есть подходящая интеграция, предлагай её.

## Что это за проект

FireTrack — веб-система учёта огнетушителей и журнала их проверок. Изначально это курсовая работа (3 семестр, РТУ МИРЭА). Теперь проект дорабатывается для себя, в удовольствие, поэтому качество важнее скорости.

Стек: Python 3.13+ (локально 3.15), FastAPI, SQLAlchemy 2, Alembic, Pydantic 2, SQLite, JWT (python-jose), passlib (pbkdf2_sha256), openpyxl. Фронтенд написан на чистом HTML, CSS и JS с Bootstrap 5 и Bootstrap Icons, без сборщика. Сервер отдаёт его из `static/`. Документация собирается через Sphinx из docstrings.

## Как запускать

Все команды выполняются из корня проекта в PowerShell.

```powershell
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
.\FireTrack.bat                             # как программа: сервер и браузер, свободный порт
python -m uvicorn main:app --reload        # для разработки: http://127.0.0.1:8000, Swagger на /docs
python -m pytest -q                        # тесты, рабочую базу не трогают
python migrate.py                          # обновить схему базы вручную (обычно не нужно)
python -m alembic check                    # модели и миграции совпадают?
```

Если меняешь `models.py`, обязательно создай ревизию в `migrations/versions/` (`python -m alembic revision -m "..."`, имена файлов вида `0005_описание.py`) и проверь `alembic check`. Для SQLite изменения существующих таблиц только через `op.batch_alter_table`.

Docker: `docker compose up -d --build`, остановить: `docker compose down`.

Пересборка документации:

```powershell
cd docs
sphinx-apidoc -o source ..\
.\make.bat html
```

Вход по умолчанию: `admin` / `admin123`, при первом входе система требует сменить пароль. Пароль админа задаётся переменной `ADMIN_PASSWORD`, но только при самом первом создании.

Переменные окружения: `DATABASE_URL`, `SECRET_KEY`, `ACCESS_TOKEN_EXPIRE_MINUTES` (по умолчанию 480), `ADMIN_PASSWORD`, `STATUS_RECALC_INTERVAL_MINUTES` (по умолчанию 60), `LOGIN_MAX_FAILURES` (5), `LOGIN_LOCK_MINUTES` (10), `FIRETRACK_HOST`, `FIRETRACK_PORT`. На порту 8000 у владельца может быть занято другой программой, поэтому `run.py` ищет свободный.

## Правила и соглашения в коде

1. Docstrings пишутся на русском в стиле Google (Args, Returns, Raises): из них собирается Sphinx. Новые модули добавляй в `docs/source` (как `status_logic.rst`) и в `modules.rst`.
2. В шапке каждого файла стоит комментарий с версией, например `# auth.py (v1.3)`. При заметных изменениях повышай её.
3. Новые эндпоинты обязательно закрывай авторизацией: на уровне роутера `dependencies=[Depends(get_current_active_user)]`, на изменяющих действиях `require_role(EDITOR_ROLES)` или `require_role([ROLE_ADMIN])`.
4. Права проверяет сервер. На фронтенде кнопки только прячутся классами `requires-edit` (видно admin и engineer) и `requires-admin` (видно только admin). Класс роли висит на `body` (`role-admin` и т.д.).
5. Любые данные пользователя вставляются в HTML только через `esc()`. В `onclick` передаются только числовые id.
6. Даты на фронте обрабатываются как строки `ГГГГ-ММ-ДД` через `formatDate` и `todayISO` из `api.js`, без `new Date(...)`, чтобы не было сдвига часового пояса.
7. Модальное окно одно на всё приложение (`#formModal`). Открывай его через `bootstrap.Modal.getOrCreateInstance`. Функции открытия форм принимают колбэк `onSuccess`. Bootstrap игнорирует `show()`, пока окно закрывается: следующее окно открывай по событию `hidden.bs.modal`.
8. Глобальные `let`-переменные (`locations`, `statuses`, `allExtinguishers`, `allEmployees`, `currentExtinguishers`, `pendingStatusFilter`) общие для всех скриптов. Через `window.xxx` к ним обращаться нельзя, они не свойства window.
9. Названия системных статусов бери из констант `status_logic.py`, не пиши строками.
10. На каждую новую фичу пиши тесты в `tests/`.
11. Каждое изменяющее действие пишется в журнал: `audit.log(...)` до `db.commit()`, для update передавай `changes=audit.diff(before, after)`.
12. Ошибки в данных исправляются, а не стираются: проверка аннулируется (`annulled_at`), и все запросы к проверкам для статусов и отчётов обязаны фильтровать аннулированные.
13. Дата последней перезарядки и испытания в карточке вычисляется по `ServiceRecords`. Напрямую её не меняй, используй `sync_extinguisher_dates`.
14. Все значения в CSV и XLSX пропускай через `safe_cell`.
15. Время из базы хранится в UTC без зоны. Отдавая время во фронт, добавляй `Z` (см. `_utc_iso` в `routers/audit_log.py`), на фронте выводи через `formatDateTime`.

## Правила расчёта статусов (уже реализованы)

| Ситуация | Статус |
|---|---|
| Проверок ещё не было | Просрочено |
| При последней проверке найден дефект: «Неисправен», а также пломба, чека или шланг «Повреждена», «Поврежден», «Отсутствует» | Требует обслуживания |
| Просрочена перезарядка и в настройках включено `recharge_overdue_needs_service` (по умолчанию да) | Требует обслуживания |
| Дата следующей проверки прошла | Просрочено |
| Иначе | Актуально |

Статусы «Списан» и «На техническом обслуживании» ставятся вручную, и массовый пересчёт их не трогает. Новая проверка сразу пересчитывает статус своего огнетушителя (кроме списанного). Если дату следующей проверки не указать, сервер подставит её по настройке `inspection_interval_months` (по умолчанию 12 месяцев, п. 5.1.1 ГОСТ Р 59641-2021). Аннулированные проверки в расчёте не участвуют.

1. Работа идёт на Windows с `core.autocrlf=true`: в рабочей папке CRLF, в репозитории LF. Не меняй окончания строк массово, иначе дифф раздуется на весь файл.

4. Одна фича — один коммит (или несколько логичных). Пушить можно после того, как прошли тесты.
5. Перед изменением схемы базы делай резервную копию `fire_extinguishers.db`: в ней реальные данные с весны 2026. `migrate.py` делает копию в `backups/` сам, но при ручных экспериментах копируй базу во временную папку и запускай сервер с `DATABASE_URL` на копию.

## Нормы и источники (сверено 06.11.2026)

1. **СП 9.13130.2009 отменён** с 1 марта 2025 года приказом МЧС России от 20.11.2024 № 1017. В V4 мы ошибочно опирались на него. Не возвращай ссылки на него и формы Г.1, Г.2, Г.3.
2. **Основной документ: ГОСТ Р 59641-2021 с Изменением № 1.** Таблица 1: вода и пена 1 раз в год (со сноской про периодичность изготовителя), порошок, CO2 и хладон 1 раз в 5 лет. П. 5.1.1: ТО включает ежегодную проверку, испытания и перезарядку и выполняется организацией с разрешением. П. 5.1.9 и 5.1.11.2: испытания раз в пять лет. П. 5.1.14: журнал можно вести электронно, но записи о ТО заверяются электронной подписью обеих сторон. Приложение А (рекомендуемое): форма А.1 карточка учёта, форма А.2 записи журнала ТО и ремонта. Рисунок 1: содержание этикетки.
3. **Срок службы:** п. 5.53 ГОСТ Р 51057-2001 («не менее 10 лет» для перезаряжаемого огнетушителя с металлическим корпусом), агрегаторы показывают стандарт как действующий.
4. **Журнал:** п. 60 ППР (постановление № 1479) требует вести учёт наличия, осмотров и сроков перезарядки в журнале эксплуатации систем противопожарной защиты.
5. Текст ГОСТ читался по неофициальной копии. Статус норм нужно сверять заново, если проект будут реально использовать для проверки надзора.
6. **Решение по статусу:** просроченная перезарядка ставит «Требует обслуживания» (раньше правила просроченного осмотра), правило отключается в настройках. Истечение срока службы и испытаний на статус не влияет, только подсвечивается в отчётах.
7. **Известное ограничение:** SQLite без AUTOINCREMENT может выдать id удалённой записи повторно, поэтому в журнале действий объект надёжнее искать по тексту (инв. номер есть в описании), чем по `entity_id`.
